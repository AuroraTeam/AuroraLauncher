# Подготовка Java и запуск игры

## Установка Java

JavaManager хранит управляемые установки по основным версиям в каталоге
`<javaDir>/<majorVersion>`. Наличие каталога больше не означает готовность Java:
менеджер находит исполняемый файл и проверяет успешный запуск `java -version`
с ожидаемой основной версией. Проверка ограничена 15 секундами. Поддерживаются
форматы версии `1.8.*`, `17.*` и аналогичные.

На Windows используется `java.exe`. Поиск поддерживает обычный `bin/java`,
macOS `Contents/Home/bin/java` и прежний вложенный bundle `zulu-*.jre`.
Это учитывает [изменение macOS bundle в Azul Zulu 2026 года](https://docs.azul.com/core/pdfs/january-2026/azul-zulu-ca-release-notes-january-2026-rev1.0.pdf).

Если установленная Java не проходит проверку, менеджер:
 
1. Запрашивает ZIP-пакет и контрольную сумму в Azul Metadata API.
2. Скачивает архив в отдельный каталог `<majorVersion>.installing-*` рядом с установками.
3. Ожидает проверку MD5 архива, распаковку и проверку SHA-1 распакованных файлов.
4. На Linux/macOS устанавливает исполняемому файлу права `0o744`.
5. Проверяет `java -version` распакованного runtime.
6. Удаляет непригодную старую установку и переименовывает проверенный runtime в основной каталог.

До завершения проверок существующий каталог не удаляется. При штатной ошибке
временный каталог и частичная загрузка очищаются в `finally`. После аварийного
завершения процесса оставшийся staging-каталог не считается установленной Java;
при следующем запуске проверяется основной каталог и при необходимости начинается
новая установка. Одновременные запросы одной версии к одному JavaManager ожидают
общий Promise. После ошибки доступна повторная попытка.

Проверка `java -version` подтверждает возможность запуска VM и основную версию;
она не заменяет проверку запуска конкретной сборки Minecraft.

## Authlib-injector

Первое использование существующего `authlib.jar` без сохранённой контрольной суммы
требует получения метаданных официального API. Проверенный SHA-256 сохраняется
в `authlib.jar.sha256`; последующие проверки совпадающего файла работают без сети
и не требуют получения последней версии при каждом запуске.

Несовпадение хеша приводит к попытке восстановления. Новый JAR скачивается
в отдельный временный каталог и заменяет основной только после успешной проверки
SHA-256. Ошибки метаданных, загрузки и проверки отклоняют `verify()`, поэтому игра
не запускается с непроверенным файлом. Повторные одновременные проверки используют
общий Promise, а после ошибки можно повторить попытку.

Сохранённая контрольная сумма предназначена для проверки целостности локального
кеша и не является отдельной подписью издателя.

## Natives и процесс игры

Starter последовательно распаковывает подходящие для текущей платформы native JAR
и ожидает завершения всех операций до возврата из `prestart()`. Ошибка распаковки
прерывает подготовку. Если несколько архивов записывают один путь, Watcher получает
контрольную сумму последней версии файла, соответствующей результату на диске.

`start()` ожидает событие `spawn` процесса игры. Ошибка создания процесса отклоняет
Promise и попадает в обработчик GameService, который останавливает Watcher и
сбрасывает состояние запуска игры. Проверка authlib выполняется до создания процесса.

## Память клиентов

Настройка памяти вынесена в `ClientMemorySettings` и временно не подключена
к интерфейсу: настройки клиентов планируются в отдельном окне. Общие настройки
не показывают выбор клиента или ползунок и не запрашивают список серверов и границы
памяти. Существующие сохранённые значения продолжают использоваться при запуске.

`ClientMemorySettings` — управляемый компонент: принимает `value` (МБ), `limits`
(`recommended`, `maximum`) и `onChange(memory)`. Он содержит ползунок, рекомендацию
и предупреждение. Будущее окно отвечает за выбор профиля, загрузку и сохранение.
Память сохраняется в `clients[].memory`, где `clientId` совпадает с UUID профиля;
для работы с массивом доступны `getClientMemory` и `setClientMemory`.

Интерфейс и Starter используют общий расчёт: по умолчанию 2048 МБ, минимум
1024 МБ, шаг ползунка 256 МБ. Рекомендуемая граница — половина физической памяти,
округлённая до ближайшего гигабайта через `Math.round`. Максимум — физическая
память минус резерв `max(2048 МБ, 25% RAM)`, также округлённый до ближайшего
гигабайта. Рекомендация не превышает максимум; нижняя граница обоих значений —
1024 МБ. Например, для 34278473728 байт рекомендация — 16384 МБ, максимум —
24576 МБ. Это ориентировочные границы, а не гарантия свободной памяти.

При превышении рекомендации компонент показывает неблокирующую подсказку под
ползунком. Дополнительное подтверждение не требуется. Сохранённое значение выше
рекомендации сохраняется при запуске; ограничение применяется только по максимуму.
Некорректное значение заменяется значением по умолчанию. Starter передаёт результат
в JVM как `-Xmx<N>M`, включая профиль без сохранённых настроек. `getMemoryLimits()`
в main-процессе самостоятельно получает физическую память через `os.totalmem()`.
IPC `getMemoryLimits` передаёт интерфейсу готовые `recommended` и `maximum` в МБ;
renderer не обращается к Node API. В тестах расчёта `totalmem()` заменяется заглушкой.

Старое общее поле `memory` не используется. Ошибки загрузки и сохранения общих
настроек показываются в интерфейсе.

## Контракт обновлений

Методы AuroraAPI явно объявляют типы ответов, в том числе
`updateRequest(): Promise<UpdatesResponseData>`, чтобы декларации пакета сохраняли
контракт списка `HashedFile[]`. После изменения API пакет нужно пересобрать перед
проверкой потребителей.

`POST /updates` требует непустое поле `dir`. Для отсутствующего ключа в индексе
клиентов сервер возвращает HTTP 404 с сообщением `Client not found`; существующий
клиент без файлов возвращает HTTP 200 и `[]`. HTTP-ошибка отклоняет запрос API
и останавливает подготовку игры. Updater сортирует копию ответа, сохраняя исходный
список. Старые серверы, возвращающие `[]` для отсутствующей сборки, невозможно
отличить от сервера с пустой сборкой без изменения их поведения.

Проверка целостности после скачивания игровых файлов и assets пока остаётся
отдельным этапом работ.

## Проверки

Из корня репозитория:

```sh
pnpm --filter @aurora-launcher/launcher exec vitest run
pnpm --filter @aurora-launcher/launcher typecheck
pnpm --filter @aurora-launcher/launcher exec electron-vite build
```

Тесты используют реальные операции с файлами и хешами в изолированных каталогах
внутри пакета launcher; каталоги удаляются после каждого теста. Сетевые запросы,
запуск JVM и Unix chmod заменяются заглушками. Отдельный тест передаёт повреждённый
ZIP реальному ZipHelper. Проверяются восстановление, повторные и одновременные
попытки, ошибки контрольных сумм, структуры macOS, порядок распаковки natives,
ошибки spawn и остановка Watcher.

Сборка через electron-vite проверяет main/preload/renderer, без создания установщика
и публикации релиза. Реальный запуск Minecraft и проверка на Linux/macOS остаются
отдельными проверками на целевых платформах.
